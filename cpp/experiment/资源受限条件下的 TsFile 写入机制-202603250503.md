# 1. 需求背景

TsFile C++ 被广泛部署于资源受限环境，包括嵌入式设备、工业边缘网关、容器化部署以及配置了内存限额的云实例。在这些场景中，进程可用内存通常在数十 MB 以内，而数据采集任务需要持续写入大量时序数据。

当前 `TsFileWriter` / `TsFileTableWriter` 要求用户自行决定三个关键参数：

- **每次写入多少行**（Tablet 的 `max_rows`）：行数过多则单次内存峰值过高，行数过少则元数据增长过快。
- **何时调用 `flush()`**：flush 决定数据何时从内存写入磁盘，直接影响内存水位。
- **何时 `close()` 当前文件并打开新文件**：TsFile 的元数据在文件关闭前持续累积在内存中，若不切换文件，最终必然超出内存上限。

这三个参数之间存在耦合关系，需要用户深入理解 TsFile 内存模型才能正确配置。对于不了解内部实现的用户，极易出现内存溢出或文件切换过于频繁导致性能劣化的问题。

**典型场景示例：**

某工厂部署了一台边缘网关，采集 50 台设备共 2500 条时序，每条序列持续采集 10 万个数据点，设备总内存 32MB，分配给写入进程的内存上限为 12MB。用户希望写完所有数据，但不知道应如何配置写入参数以避免 OOM。


# 2. 产品调研

## 2.1 客户使用场景调研

根据资源受限环境下的典型部署，用户需求可归纳为以下三类：

| 场景 | 描述 | 对写入参数的了解程度 |
|:---|:---|:---|
| 嵌入式/边缘设备 | 内存严格受限（< 32MB），长时间持续采集 | 几乎不了解，只知道总内存上限 |
| 容器化部署 | 设置了 cgroup 内存限额，避免影响同节点其他服务 | 知道内存上限，不了解 TsFile 内部参数 |
| 批量历史数据导入 | 将大批量历史数据写入 TsFile，内存有限 | 知道总数据量，但不了解最优批次大小 |

三类场景的共同点：用户知道内存上限，但不知道应设置多大的批次和何时切换文件。

## 2.2 常见竞品调研

| 产品 | 内存控制方式 | 对用户的要求 |
|:---|:---|:---|
| Apache Parquet（C++）| 通过 `row_group_size` 控制每组数据大小 | 用户需自行估算每行字节数再换算 |
| InfluxDB IOx | 内部自动 compaction，用户设置全局内存上限 | 全自动，无需用户干预 |
| HDF5 | 通过 chunk size 控制分块 | 用户需手动设置，文档复杂 |
| LevelDB / RocksDB | write buffer size 全局配置 | 用户设置 buffer 大小，无文件切换概念 |

**差距分析：** 相比 InfluxDB IOx 等新一代系统，TsFile C++ 当前将内存管理的复杂性完全暴露给用户。本需求目标是提供类似"全自动"的写入体验，同时保留用户对参数的可见性和可调性。


# 3. 功能定义

## 3.1 功能描述

提供 `MemConstrainedWriter` 类，用户只需指定**内存上限**和**表结构（TableSchema）**，写入器自动完成以下工作：

1. 根据内存上限和 schema 计算推荐的每次写入行数（`rows_per_tablet`）。
2. 每次 `write_table()` 调用后自动执行 `flush()`，将数据落盘释放内存。
3. 追踪元数据累积量，在接近内存上限时自动 `close()` 当前文件并打开下一个文件。
4. 管理输出文件的命名和编号，用户完成后可查询所有生成的文件列表。

用户无需手动调用 `flush()` 和 `close()`，无需了解 TsFile 的内存模型细节。

## 3.2 功能定义

### 3.2.1 写入策略计算（`compute_strategy`）

提供静态方法，根据内存约束和 schema 计算写入策略，可独立于写入器使用：

**输入：**
- `mem_limit_bytes`：内存上限（字节）
- `table_schema`：表结构，包含列名、数据类型、列类别（TAG/FIELD）
- `n_devices`：预期设备数量（唯一 TAG 组合数），填 0 表示未知
- `total_rows_per_device`：每设备总行数，填 -1 表示未知

**输出（`WritingStrategy`）：**

| 字段 | 含义 |
|:---|:---|
| `rows_per_tablet` | 建议的每次 Tablet 行数（F） |
| `flushes_per_file` | 每个文件最多 flush 次数（K），-1 表示无需切换文件 |
| `estimated_peak_mem` | 按此策略的预估峰值内存（字节） |

**计算策略：**

- 若 `total_rows_per_device > 0` 且 `n_devices > 0`：采用 EOQ 最优解，最小化内存占用。
  ```
  F = √(total_rows × n_devices × b / s)
  K = total_rows / F
  ```
- 否则（流式写入或设备数未知）：采用对半分预算策略，最大化单文件容量。
  ```
  F = M_avail / (2 × s)
  K = M_avail / (2 × n_devices × b)
  ```

其中 `s` 为每行综合字节数，`b` 为每设备每次 flush 的元数据增量，均由 schema 自动推导。

### 3.2.2 受限写入器（`MemConstrainedWriter`）

**构造参数：**

| 参数 | 类型 | 说明 |
|:---|:---|:---|
| `mem_limit_bytes` | `int64_t` | 内存上限（字节） |
| `output_dir` | `string` | 输出目录 |
| `file_prefix` | `string` | 文件名前缀，生成 `prefix_0000.tsfile`、`prefix_0001.tsfile` ... |
| `table_schema` | `shared_ptr<TableSchema>` | 表结构 |
| `n_devices` | `int` | 设备数，默认为 0（未知，自动追踪） |
| `total_rows_per_device` | `int64_t` | 每设备总行数，默认为 -1（未知） |

**主要方法：**

| 方法 | 说明 |
|:---|:---|
| `write_table(tablet)` | 写入数据，自动 flush，必要时自动切换文件 |
| `close()` | 完成所有写入，关闭最后一个文件 |
| `rows_per_tablet()` | 返回建议的 Tablet 行数，用于创建 Tablet |
| `strategy()` | 返回当前生效的写入策略（可用于日志和诊断） |
| `created_files()` | 返回本次写入创建的所有文件路径列表 |

### 3.2.3 设备数未知时的自适应追踪

当 `n_devices = 0` 时，写入器进入动态追踪模式：

- 每次 `write_table()` 后调用 `tablet.find_all_device_boundaries()` 获取本次 Tablet 中的设备数。
- 若发现新设备（超过历史最大值），实时更新元数据预算估算，收紧切换阈值。
- 该方法基于列的逐元比较实现，性能优于逐行扫描。
- rotate 后重置设备计数，从下一个文件重新开始追踪。

## 3.3 非功能定义

### 3.3.1 性能要求

| 指标 | 要求 |
|:---|:---|
| rotate 判断开销 | 每次 `flush()` 后执行一次整数乘法，延迟 < 1 μs |
| 内存监控方式 | 不依赖 `ModStat`（`ATOMIC_FAA` 热路径），仅使用公式估算 |
| 内存控制精度 | 实际峰值内存不超过用户指定上限的 115%（公式误差 + 安全裕度） |
| 写入吞吐影响 | 相比直接使用 `TsFileTableWriter`，额外开销 < 1% |

安全裕度（`SAFETY_FACTOR = 0.85`）：在元数据预算耗尽前 15% 触发 rotate，用于吸收公式估算误差。

### 3.3.5 创新点

1. **公式驱动的零开销内存控制**：基于 TsFile 内存模型（M_init + M_data + M_meta）推导出解析解，不引入任何运行时内存采样开销。

2. **EOQ 模型应用**：将经济订货量（Economic Order Quantity）模型引入时序写入场景，在数据批次大小（决定内存峰值）与 flush 次数（决定元数据增量）之间求得最优平衡点。

3. **自适应设备追踪**：利用 `find_all_device_boundaries()` 的列式比较实现，以极低开销实现设备数量的动态感知，在设备数未知场景下仍能保证内存不超限。


## 3.5 场景示例

### 场景一：已知设备数和总数据量（最优配置）

```cpp
// 50 个设备，每设备 10 万行，内存上限 10MB
auto schema = std::make_shared<TableSchema>("sensor", columns);

MemConstrainedWriter writer(
    10 * 1024 * 1024,  // 10MB 内存上限
    "/data/output",
    "sensor",
    schema,
    50,                // 50 个设备（已知）
    100000             // 每设备 10 万行（已知）
);

// 查询推荐的 Tablet 行数
int F = writer.rows_per_tablet();  // 系统自动计算最优批次大小

while (has_more_data) {
    Tablet tablet("sensor", schema_vec, F);
    fill_tablet(tablet, cur_row, F);
    writer.write_table(tablet);    // flush / rotate 全自动
}
writer.close();

// 查看生成的文件列表
for (const auto& path : writer.created_files()) {
    process(path);  // /data/output/sensor_0000.tsfile, sensor_0001.tsfile ...
}
```

### 场景二：设备数未知（动态追踪模式）

```cpp
// 不知道有多少设备，只知道内存上限
MemConstrainedWriter writer(
    8 * 1024 * 1024,   // 8MB 内存上限
    "/data/output",
    "data",
    schema             // n_devices 省略，默认 0（动态追踪）
);

int F = writer.rows_per_tablet();

while (stream.has_next()) {
    auto batch = stream.next_batch(F);  // 每批 F 行，设备 TAG 值不固定
    writer.write_table(batch);
    // 内部自动统计本次 Tablet 包含多少个设备，
    // 动态调整切换阈值，保证内存不超限
}
writer.close();
```

### 场景三：仅查询策略，不创建写入器

```cpp
// 在正式写入前预估策略
auto strategy = MemConstrainedWriter::compute_strategy(
    12 * 1024 * 1024,  // 12MB
    schema,
    50,                // 50 设备
    100000             // 10 万行
);

printf("推荐批次大小: %ld 行\n", strategy.rows_per_tablet);
printf("每文件最多 flush: %ld 次\n", strategy.flushes_per_file);
printf("预估峰值内存: %.1f MB\n", strategy.estimated_peak_mem / 1e6);
```

# 4. 自测及测试场景建议

## 4.1 策略计算正确性

| 测试用例 | 输入 | 期望结果 |
|:---|:---|:---|
| 总量已知，内存充足 | M=12MB, D=50, R=100000, int32×50列 | F≈7500, K≈22, peak≈11MB |
| 总量已知，内存紧张（EOQ 超限） | M=5MB, D=50, R=100000, int32×50列 | 退化为对半分策略 |
| 总量未知，设备数已知 | M=10MB, D=50, total=-1 | F=M_avail/(2s)，K=M_avail/(2B) |
| 设备数未知 | M=10MB, D=0, total=-1 | D 初始按 1 估算，不报错 |
| 内存上限过小 | M=500KB | 返回错误或 F=1（最小值） |

## 4.2 自动 flush 与 rotate 行为

| 测试用例 | 验证点 |
|:---|:---|
| 写入 K+1 次 Tablet 后，应生成第 2 个文件 | `created_files().size() == 2` |
| rotate 后 flush_count 重置为 0 | 下一文件能容纳完整 K 次 flush |
| 最后一个文件 `close()` 后可正常读取 | 用 `TsFileReader` 验证数据完整性 |
| 总写入数据量与各文件数据量之和一致 | 无数据丢失或重复 |

## 4.3 动态追踪模式

| 测试用例 | 验证点 |
|:---|:---|
| 前几批 Tablet 设备少，后续增多 | K 随设备数增多而收紧，最终 rotate 时机不晚于已知模式 |
| 每批 Tablet 只含 1 个设备 | 逐步发现设备，不提前 rotate |
| rotate 后首批 Tablet 包含所有设备 | 立即收紧 K，行为与已知模式一致 |

## 4.4 内存上限保证

| 测试用例 | 验证点 |
|:---|:---|
| 全程写入，用 Valgrind/Massif 测量峰值 | 实际峰值 ≤ mem_limit_bytes × 1.15 |
| STRING 列场景 | 内存不超限（32字节估算 + 安全裕度） |

## 4.5 生成文件可读性

| 测试用例 | 验证点 |
|:---|:---|
| 多文件场景，用标准接口逐一读取 | 数据类型、值、时间戳与写入一致 |
| 最后一个文件（非满文件）可正常读取 | 边界条件不损坏文件结构 |


# 附录：历史内容及讨论记录

## 2026年3月25日 内部讨论

- 讨论关键记录及结论：
  - 内存模型确认：M_total = M_init + M_data + M_meta，三部分特征不同（固定/周期/单调递增）。
  - 确认 M_init ≈ 900KB，M_data = s×F（flush 后释放），M_meta = K×D×b（close 才写盘）。
  - 公式误差实验验证：5–15%，通过 SAFETY_FACTOR=0.85 吸收。
  - 排除 ModStat 方案：`ATOMIC_FAA` 热路径开销在嵌入式场景不可接受，且精度超出所需。
  - 确认使用 `find_all_device_boundaries()` 进行动态设备追踪：列式比较，性能优于逐行扫描。
  - 设计决策：直接包装 `TsFileWriter`（而非 `TsFileTableWriter`），以便 rotate 时精确控制 `open()` 和 `register_table()`。
